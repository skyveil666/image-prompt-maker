# 11. UI 重複一覧

> **目的**: 現状の UI に存在する「同じ情報が複数箇所に表示されている」「同じ操作を提供する複数 UI が存在する」状態を棚卸しし、整理候補と整理方針を整理する。
> **依拠**: [master-plan-v1.md](./master-plan-v1.md) §13 機能間の連携マトリックス

---

## 1. 重複の分類

本書では「重複」を3カテゴリに分ける:

| カテゴリ | 定義 | 対応方針 |
|---|---|---|
| **A. 表示重複** | 同じ情報が複数箇所に表示されている | 主表示を決め、副表示は省略 or リンク化 |
| **B. 操作重複** | 同じ機能を起動する UI が複数ある | 1箇所に集約、他は廃止 or 補助化 |
| **C. 概念重複** | 似た概念が別名・別 UI で並走している | 命名統一・統合・廃止のいずれか |

## 2. 重複一覧

### 重複 #1 [カテゴリ A+B]: 「守るもの」表示・操作の三重化

**箇所**:
- [ProtectionBar.tsx](../src/components/ProtectionBar.tsx) — 「守るもの」表示 + 個別ロック + faceLock + 安全モード
- [LockToggles.tsx](../src/components/LockToggles.tsx) — bodyPoseLock / colorMoodLock / compositionLock トグル
- [FaceLockSwitch.tsx](../src/components/FaceLockSwitch.tsx) — faceLock 大型バナー

**状況**:
- ProtectionBar は LockToggles と FaceLockSwitch を内包しているはずだが、コンポーネント単位では分離されている
- 同じ faceLock 値を複数箇所で表示・操作可能

**重要度**: 🔴 高

**整理方針**:
- [10_protection-bar常時表示.md](./10_protection-bar常時表示.md) で新 `GlobalProtectionBar.tsx` に統合
- LockToggles / FaceLockSwitch は新 ProtectionBar の内部表示として再利用 or 廃止

### 重複 #2 [カテゴリ A]: 「今何が効いているか」の二重表示

**箇所**:
- [ReflectionStatusBar.tsx](../src/components/ReflectionStatusBar.tsx) — 反映状態のサマリ表示
- [DuplicateAnalysisPanel.tsx](../src/components/DuplicateAnalysisPanel.tsx) ヘッダ部 — 「policyApplied なら ✓ 反映中」表示

**状況**:
- ReflectionStatusBar は **全体の反映状態**（scopes / favoriteLearn / zozo / 神引き / 色重み）を集約表示
- DuplicateAnalysisPanel ヘッダは **重複分析の反映状態のみ**を表示
- 表示粒度は異なるが、ユーザーから見ると「どちらを見れば良い？」になる

**重要度**: 🟡 中

**整理方針**:
- **役割分離を明示**: ReflectionStatusBar = 全体サマリ / DuplicateAnalysisPanel = 自パネル内のローカル状態
- DuplicateAnalysisPanel ヘッダの表示を「重複分析: 反映中」のように **自パネル限定の文言に統一**
- ReflectionStatusBar は ProtectionBar と統合せず、引き続き「生成補助系の状態」を担当（保護系は ProtectionBar）

### 重複 #3 [カテゴリ A+C]: skyveil 好み分析の表示二重化

**箇所**:
- [SkyveilBar.tsx](../src/components/SkyveilBar.tsx) — メインの skyveil トグル + プロファイル展開
- [DuplicateAnalysisPanel.tsx](../src/components/DuplicateAnalysisPanel.tsx) 内 `RealAnalysisCard` — 好み分析レポート展開（L280-379）

**状況**:
- SkyveilBar はメインエリア（ControlPanel配下）に常設
- DuplicateAnalysisPanel 内にも同じ `preferenceProfile` を表示するカードが存在
- 両方とも「分析実行ボタン」「サンプル数表示」「プロファイル表示」を持つ

**重要度**: 🟡 中

**整理方針**:
- 操作（ON/OFF / 強度 / 実行ボタン）は **SkyveilBar に一元化**
- DuplicateAnalysisPanel 内の RealAnalysisCard は **読み取り専用サマリ + 「SkyveilBar を開く」リンク** に縮小
- または DuplicateAnalysisPanel 側を完全に削除して SkyveilBar のみに統一

### 重複 #4 [カテゴリ C]: identityRisk の二重実装

**箇所**:
- フロント: [src/lib/identityRisk.ts:41-101](../src/lib/identityRisk.ts#L41) `analyzeIdentityRisk()`
- サーバ: [server/src/scopeFilter.ts:211-266](../server/src/scopeFilter.ts#L211) `applyIdentityShield()`

**状況**:
- 同じ「同一性リスク採点」が **フロント版（表示用）** と **サーバ版（実注入用）** で2回計算される
- スコア定義はおおむね揃っているが、完全同期は保証されていない
- フロント版は UI ライブ表示・サーバ版は実プロンプト注入が用途

**重要度**: 🟡 中（実害は少ないが、ロジック乖離の温床）

**整理方針**:
- **採点ロジックを単一ソースに**: 共通の TypeScript 関数として `lib/identityRiskCore.ts` を作成し、フロント・サーバ両方が import
- またはサーバの採点結果を `IdentityShieldSummary` で返し、フロントは表示のみに徹する（事前計算が必要なため難しい）
- 短期は **目検同期**、中期は **共通モジュール化**

### 重複 #5 [カテゴリ A]: PromptCard 内のロック表示と ProtectionBar の重複

**箇所**:
- [PromptGuardSection.tsx:210-229](../src/components/PromptGuardSection.tsx#L210) — 「変更対象ロック一覧」（変更する項目/変更しない項目/固定ルール）
- ProtectionBar — メインエリアの保護状態表示

**状況**:
- PromptGuardSection は **生成済みプロンプトに対する事後ロック確認**
- ProtectionBar は **生成前のライブ設定状態**
- 同じ情報源（scopes + locks）から異なる視点で表示している

**重要度**: 🟢 低（用途が分かれており、両方に価値がある）

**整理方針**:
- **維持**: 生成前（ProtectionBar）と生成後（PromptGuardSection）の使い分けを docs で明示
- 表現を統一（同じアイコン・同じラベル）して「同じ概念」と分かるようにする

### 重複 #6 [カテゴリ A]: 評価表示の二重化

**箇所**:
- [PromptCard.tsx](../src/components/PromptCard.tsx) — カード単位の評価 UI（5段階＋軸別 👍👎）
- [DuplicateAnalysisPanel.tsx](../src/components/DuplicateAnalysisPanel.tsx) — 評価サンプル統計

**状況**:
- PromptCard は個別画像への評価入力
- DuplicateAnalysisPanel は集計表示

**重要度**: 🟢 低（用途が明確に分かれている）

**整理方針**:
- **維持**: 入力（カード）と集計（パネル）は本質的に別物
- 表示要素を統一すること程度

### 重複 #7 [カテゴリ A]: ロック状態カウンタの分散

**箇所**:
- ProtectionBar の「○件ON」バッジ
- ReflectionStatusBar の「保護: 顔・体型ON」表記
- PromptCard ヘッダの「コピー時にロック数表示」

**状況**:

**重要度**: 🟢 低

**整理方針**:
- `useLockSummary()` のような Hook を作って単一ソース化
- 3箇所がすべて同じ Hook を参照する形に

### 重複 #8 [カテゴリ C]: 「好みプロファイル」の3層

**箇所**:
- [favoriteProfile.ts](../src/lib/favoriteProfile.ts) — ヒューリスティック集計
- [preferenceProfile.ts](../src/lib/preferenceProfile.ts) — Gemini 実分析結果
- [skyveilProfile.ts](../src/lib/skyveilProfile.ts) — 上記2つ + 他3系統を統合

**状況**:
- 3つの「Profile」が並走しており、命名から責務の違いが伝わりにくい
- ユーザーから見て「お気に入り傾向」「好み傾向」「skyveil 傾向」の違いは不明瞭

**重要度**: 🟡 中（コード重複ではなく **概念重複**）

**整理方針**:
- **層を明示**: docs で「Layer 1 = favoriteProfile（基礎ヒューリスティック）」「Layer 2 = preferenceProfile（AI実分析）」「Layer 3 = skyveilProfile（統合）」と階層図化
- 命名を維持するなら、UI 上では **skyveilProfile のみ表示**し、内部実装の Layer 1/2 はユーザーに見せない
- skyveil 内部の入力 5系統の説明は技術文書のみ

---

### 重複 #9 [カテゴリ B]: 「反映」ボタンの分散

**箇所**:
- DuplicateAnalysisPanel 内の「✓ 提案を反映」ボタン
- SkyveilBar 内の「今回だけ反映」ボタン
- 成功パターンの「この型を現在設定に反映」ボタン
- ColorWeightGrid 内の「✨ 提案を反映」「全上書き」

**状況**:
- 「反映」というアクションが複数文脈で存在
- それぞれ作用範囲が異なる:
  - 重複分析の反映 = motifControls / comboControls
  - skyveil の反映 = preferenceProfile / favoriteTraits / ratingBias
  - 成功パターンの反映 = scopes
  - 色重みの反映 = colorWeights（常時送信のため「反映」というより「保存」）

**重要度**: 🟡 中（用語の混乱を招く）

**整理方針**:
- **「反映」という単語の意味を統一**: 「次回生成に効く状態にする」
- 各反映ボタンに **影響範囲のチップ** を付ける（例: 「反映 (重複制御のみ)」「反映 (skyveilのみ)」）
- もしくは、グローバルな「✓ 全分析を反映」ボタンを 1 つ追加（影響範囲をモーダルで確認）

---

### 重複 #10 [カテゴリ A]: NG / 禁止表示の分散

**箇所**:
- [NgInput.tsx](../src/components/NgInput.tsx) — ユーザー入力 NG
- [ForbiddenTokens.tsx](../src/components/ForbiddenTokens.tsx) — 意味展開された禁止トークン
- 色重みの「0=完全禁止」設定
- 重複分析の「0 = 一発NG」設定
- 構成コンボの「block」設定

**状況**:
- 「これを出さないでほしい」の表現が **5箇所** に分散
- 最終的に `mergeForbiddenIntoNgList` 等で 1 つの NG リストに集約されているが、UI からはどこを編集すれば反映されるか分かりにくい

**重要度**: 🟡 中

**整理方針**:
- **NG入力センター** のような統合ビューを作る（任意のサブセクションを開く）
- 各 NG ソースに「これは [Source] に保存されます」のラベルを表示
- 最終的に生成プロンプトに反映される NG リスト全文を **PromptGuardSection で表示** する（既に一部対応済み）

## 4. 整理時の遵守事項

[01_UI構成.md §レイアウト制約](./01_UI構成.md) より:

> - **変更可**: 文字サイズ / 色 / ウェイト / placeholder色
> - **変更禁止**: ボタンサイズ / カードサイズ / 余白 / 配置 / レイアウト / 枠線 / テーマカラー / コンポーネント構造

→ **コンポーネント構造の変更を伴う整理は、必ずユーザー承認を得てから着手**する。
